# HAPI OS Launcher — Build Roadmap and CI/CD Recommendations

**Status:** implementation roadmap; not a claim that native launcher binaries already exist  
**Canonical architecture:** `carbonactual/carbonactual`  
**Constitutional authority:** HAPI World `CANON.md`

## 1. What “HAPI OS” means in this build

The practical first product should be a **cross-platform launcher application that runs on top of supported host operating systems**, not a replacement kernel or a new operating system distribution. It should present one coherent HAPI experience while using the host platform's browser, application lifecycle, permissions, notifications, storage and native integration capabilities.

“Windows, Android, macOS, Linux and all other operating systems” is a product ambition, not a support claim. Support must be declared and tested per platform, architecture and release channel. A successful web build does not prove a native Windows, Android, macOS or Linux package.

## 2. Repository boundaries discovered

| Repository | Current responsibility | Evidence and implication |
|---|---|---|
| `carbonactual/carbonactual` | Canonical ecosystem contracts, architecture and conformance | This repository currently has Node.js validators and architecture tests. The tracked tree does not contain a Rust workspace, Tauri shell, Android Gradle project, Xcode project, C11 shared-memory ring source or HCPQL implementation. |
| `carbonactual/abba` | ABBA intelligence and orchestration; includes `carbon-actual-os/` command-center app | The app is a Next.js web application. Its package manifest has no committed npm/pnpm/yarn lockfile in the inspected tree, so deterministic `npm ci` is not ready yet. |
| `carbonactual/Carbon-Actual-` | Platform/runtime substrate | It contains a Node.js implementation/test surface and Ash-Phoenix continuity/security contract material, including `tests/architecture/continuity-ash-phoenix.test.mjs`. It does not currently contain the requested Rust/Tauri/Gradle/Xcode/C11/HCPQL launcher stack. Its `omnii/` subtree is historical provenance, not the target for new runtime work. |

The public canonical repository cannot safely assume access to the separate private ABBA and platform-runtime repositories. Cross-repository orchestration requires an explicitly provisioned, least-privilege GitHub App or equivalent credential. No token is embedded in this workflow.

## 3. What this first pipeline does

`.github/workflows/hapi_ci_cd.yml` is the first **canonical CI and launcher-readiness gate**:

- Runs existing canonical law, ecosystem-kernel, ecosystem-overview, product-recipe and global-readiness validators on Linux, macOS and Windows using Node.js 22.
- Runs the repository's complete Node.js test discovery with `node --test`.
- Runs CodeQL security analysis for JavaScript/TypeScript with the extended query suite.
- Dependency review is a recommended next activation once the app/runtime repositories have committed dependency manifests and lockfiles. The canonical repo currently has no root manifest, so this first pass does not run a dependency-review action here.
- Publishes a machine-generated readiness inventory showing which native platform project manifests and source components are actually present in this repository.

The CI matrix validates canonical contracts on three host operating systems. **It does not yet compile or package a HAPI launcher for those operating systems.** There is intentionally no deployment job and no `|| true`: a compiler, test or security failure must remain a failure.

## 4. Recommended implementation sequence

### Phase A — Make the launcher usable everywhere first

1. Stabilize the existing `carbonactual/abba/carbon-actual-os` web application and its HAPI/ABBA entry flow.
2. Commit a lockfile generated by the package manager selected for that app; pin the Node.js version and replace floating dependency declarations such as `latest` with reviewed versions.
3. Add responsive layouts, install metadata, icons, offline/poor-network behavior and a service worker where the product's data/security model permits.
4. Test it in current browsers on Windows, macOS, Linux, Android and iOS. Treat this as a **PWA/web distribution** milestone, not native OS integration.

This is the lowest-cost route to a broadly accessible launcher while the native shell is being designed.

### Phase B — Add a native shell when host integration is required

Evaluate **Tauri 2** as the leading open-source candidate for one shared web frontend with a Rust native layer. Its platform documentation lists Windows, macOS, Linux, Android and iOS targets. The host prerequisites are different: for example, Linux requires WebKitGTK/system packages, Windows requires the Microsoft C++ build tools and WebView2, macOS/iOS use Xcode toolchains, and Android requires the Android toolchain.

References: [Tauri](https://tauri.app/) · [Tauri prerequisites](https://tauri.app/start/prerequisites/) · [Tauri source repository](https://github.com/tauri-apps/tauri).

Before adoption, make and record a decision on the native shell, permissions, updater, signing, deep links, background services, accessibility and mobile lifecycle. Tauri is a recommendation to evaluate, not a framework already installed in the repositories.

### Phase C — Build and test native targets separately

Create real platform projects and then add dedicated jobs. Do not cross-compile every target from Ubuntu or hide missing toolchains.

| Target | Build environment to add | First release gate |
|---|---|---|
| Windows x64 / ARM64 | Windows runner with MSVC and WebView2 prerequisites | Debug and release package; install/launch smoke test; signing plan |
| macOS Apple silicon / Intel | macOS runner with Xcode | App bundle/DMG; signing and notarization path; launch smoke test |
| Linux x64 / ARM64 | Linux runners with required WebKitGTK and packaging libraries | AppImage/deb/rpm choice; launch smoke test on supported distributions |
| Android ARM64 | Android-capable runner with JDK, SDK and NDK | Debug APK, emulator/device install test, permissions and lifecycle test |
| iOS ARM64 | macOS runner with Xcode | Simulator build, device build, signing/profile and lifecycle checks |

Start with one primary architecture per platform, prove the release path, then expand to additional CPU architectures. A target becomes “supported” only after a repeatable build, installation and smoke test are green.

### Phase D — Native IPC and C11

The proposed source path `native/shm_ring/uef_shm_ring.c` is not present in the canonical repository. Do not create an empty directory and treat that as an implementation. When the source and its API contract exist:

- Use CMake or another explicit native build description and require C11.
- Compile with strict warnings treated as errors; do not suppress failure with `|| true`.
- Add unit tests for wraparound, full/empty states, concurrent access, memory ordering and process restart/recovery.
- Run sanitizers (AddressSanitizer/UndefinedBehaviorSanitizer where supported) and separate platform-specific tests.
- Define a portable IPC abstraction and document where shared memory is unavailable or inappropriate, particularly across mobile app sandbox/lifecycle boundaries.

### Phase E — HCPQL and assurance

No HCPQL implementation source is present in the canonical repo tree. Before adding a CI verifier, define the ledger interface, event schema, proof format, threat model, key lifecycle, deterministic replay expectations and failure/recovery semantics.

Do not invent a cryptographic primitive or implement custom post-quantum cryptography. Select vetted, standardized algorithms and reviewed libraries through a documented security decision. Tests should prove append integrity, replay determinism, malformed-input rejection, proof verification, key rotation and recovery. The Ash-Phoenix contract/tests already present in the platform/runtime repository should be run in that repository's own CI; they should not be represented as having run in this repo.

### Phase F — Release and deployment governance

Keep deployment out of CI until there is an actual packaged application and signed release process. The eventual release flow should be:

`tag → build per platform → test/install smoke test → generate SBOM and provenance → sign artifacts → human approval → publish`

The release job should require an explicit approval environment and a narrowly scoped publishing credential. No bot or CI job should infer release authority from a successful build. ABBA may prepare and recommend a release; the appropriate human authority/SEAL gate must authorize the state-changing publish action.

## 5. Security and supply-chain recommendations

1. Keep workflow permissions least-privilege and use immutable action commit SHAs. Dependabot is configured to propose weekly GitHub Actions updates; review each update rather than silently accepting it.
2. Enable and review GitHub secret scanning and push protection where available in repository security settings. A green CodeQL run is not proof that secrets are absent or that all languages/repos have been scanned.
3. Enable the dependency graph and Dependabot security updates when manifests/lockfiles exist. Add dependency review to every app/runtime repo that owns its own dependency graph.
4. Generate an SBOM and build provenance for release artifacts; sign packages using protected signing credentials, not repository source files.
5. Keep the HAPI authority boundary: CI may validate, report and build; it must not approve its own release, modify canonical policy, or deploy production without explicit authorization.

## 6. Promotion criteria

A platform is promoted from “planned” to “supported” only when the repository has the actual platform project, reproducible dependencies, CI build evidence, installation/launch tests, security review, release/signing path and documented recovery/update behavior.

Until then, the launcher-target inventory must continue to report that target as **not present** or **not verified**, rather than green.
