# Carbon Actual Integration & Provider Policy

**Status:** CANONICAL INTEGRATION POLICY  
**Authority:** Carbon Actual operating-spine contracts + HAPI World constitutional boundary

## Purpose

Carbon Actual must remain interoperable, replaceable, economically sustainable and deployable across sovereign, self-hosted, open-source and hosted environments.

Provider research is input. It is not constitutional architecture.

## Provider selection rule

For every capability, ABBA and product builders should evaluate the field before selecting an implementation.

Selection dimensions include:
- capability fit;
- interoperability;
- open standards;
- source availability;
- self-hostability;
- portability;
- security;
- privacy;
- reliability;
- latency;
- cost;
- licensing;
- maintenance;
- ecosystem maturity;
- provider concentration risk;
- exit/migration difficulty;
- data portability;
- jurisdiction;
- observability;
- failure/recovery behavior.

No provider is permanently designated “the Carbon Actual provider” merely because it is presently preferred.

## Open-first principle

Where materially suitable, prefer:
1. open standards;
2. free/open-source software;
3. self-hostable implementations;
4. vendor-neutral protocols;
5. portable data formats;
6. replaceable adapters.

Hosted/commercial providers remain valid adapters when they provide required capability, reliability, compliance, scale or operational value.

Commercial dependency must never become constitutional dependency.

## Free does not mean mandatory

“Free always” applies to avoiding unnecessary lock-in and unnecessary paid dependencies at the architecture level.

A production deployment may legitimately incur:
- infrastructure cost;
- network/telecom cost;
- regulated service cost;
- provider API cost;
- operational labor;
- storage/compute cost;
- licensing cost where unavoidable.

Such costs must be explicit and represented in the economic/value boundary rather than hidden.

## Adapter rule

Every external provider belongs behind a capability adapter wherever practical:

`canonical capability → adapter → provider`

The provider may change without changing canonical semantic meaning.

Provider-specific identifiers must not become universal identity, authority, event, ledger or value primitives.

## Fallback and substitution

A capability should be able to declare:
- primary implementation;
- alternate implementation;
- degraded/local mode;
- unavailable state;
- migration target.

ABBA may compare or route among providers according to context and authority.

A fallback does not silently change the contract.

## Data portability

Material provider-backed state should preserve:
- canonical identity/reference;
- provenance;
- provider identity;
- external identifier;
- creation/update time;
- state;
- transformation history;
- export path;
- migration notes.

Provider exit must not destroy canonical continuity where preservation is legally and technically possible.

## Secret handling

Provider credentials:
- never enter architecture documents;
- never enter product manifests;
- never enter prompts or logs;
- never become repository dependencies;
- must use controlled secret custody.

Provider activation status must distinguish:
`scouted → specified → configured → tested → active → degraded → revoked → retired`

## AI provider neutrality

AI models/providers are interchangeable capability sources.

The architecture must not assume:
- one model family;
- one vendor;
- one agent framework;
- one vector database;
- one UI framework;
- one cloud;
- one workflow engine.

ABBA owns orchestration and capability interpretation, not a permanent provider.

## Communication/provider neutrality

Communication implementations may use multiple transports/providers for:
- messaging;
- voice/video;
- meetings;
- notifications;
- presence;
- media;
- agent communication.

The communication contract is stable while providers remain replaceable.

## Database/storage neutrality

Carbon Actual contracts should remain expressible over PostgreSQL-compatible, file/journal, object storage or other compliant persistence implementations.

A product may use a specific database for implementation reasons without changing canonical persistence semantics.

## Blockchain neutrality

Blockchain networks are adapters.

Network choice must remain replaceable and must never redefine:
- ownership;
- identity;
- rights;
- token eligibility;
- value semantics;
- settlement truth.

## Evaluation and routing

The Swarm/Team model is the field-evaluation mechanism:
- Swarm = available capability field.
- Team = purposeful composition.
- ABBA = evaluation/orchestration intelligence.
- Provider = replaceable implementation.

The goal is not to crown a permanent winner. It is to maintain a useful, evidence-backed capability field.

## Governance

Consequential provider activation requires the applicable authority, policy, evidence and security controls.

High-impact provider changes should preserve:
- before/after evidence;
- dependency mapping;
- rollback path;
- cost impact;
- security impact;
- continuity impact;
- migration state.

## Invariants

1. Provider is not authority.
2. Provider is not ontology.
3. Provider is not identity.
4. Provider is not the canonical ledger.
5. Provider is not the constitutional source.
6. A hosted service is not mandatory merely because it is convenient.
7. A free/open implementation is not automatically suitable without evidence.
8. Commercial use may be legitimate when costs and dependencies are explicit.
9. Exit must remain possible where technically and legally feasible.
10. No vendor lock-in becomes a hidden ecosystem law.
