## 1. Purpose

This document is the overview layer used to align the ecosystem's laws, doctrines, common functions, domains, products, SWIRMs and TEAMs.

The governing distinction is:

`CANON → DOCTRINES → KERNEL → COMMON FUNCTIONS → DOMAIN CIRCUMFERENCE → SWIRMs → TEAMs → WORKFLOWS → PRODUCTS/INTERFACES`

A product is a projection into a domain. A domain is not a product. A SWIRM is not a product. A TEAM is not a new authority layer.

The domain circumference method applies to every domain, not only the domains already implemented.

## 6. How domains, SWIRMs and TEAMs relate

### Domain

Defines the full real-world circumference of a field of activity.

### SWIRM

Defines the available capability field for a recurring function. It answers:

`What equivalent/adjacent capabilities exist, and which implementations can perform this function?`

SWIRM selection considers capability coverage, specialization, evidence, availability, cost/value, latency, interoperability, openness, privacy, security, maturity, dependencies, risks and context suitability.

### TEAM

Defines a temporary or durable cross-functional composition for a specific intent/mission.

It answers:

`Which capabilities from which SWIRMs must work together here?`

A TEAM can cross multiple domains. Its members can change without changing the domain model or constitutional semantics.

### Workflow

Sequences the selected TEAM's work.

### Product

Provides a projection/interface into a domain or mission. It consumes the same shared SWIRMs/TEAMs; it does not recreate them.

## 10. Build law

Before substantial product/domain implementation:

`scope the circumference → map kernel facets → map doctrines/boundaries → map existing capabilities → assign functional SWIRMs → identify cross-domain TEAMs → map providers/adapters → define evidence/authority gates → populate the canonical registry → test → build → observe → learn`

A product is incomplete when its UI exists but the underlying domain circumference, shared capabilities, authority boundaries, evidence path, value path and cross-domain compositions are undefined.

## 11. Open-world rule

The atlas is deliberately open to all countries, subdivisions, organizations, institutions, associations, clubs, enterprises, startups, markets, software, AI, agents, open source, commercial providers, public information systems and future/unknown entities. Discovery does not imply authority, access or truth.

No catalog claims that the world's systems are exhaustively enumerated at one moment. The registry is continuously extensible and evidence-driven.

## 12. Nonredundancy and replacement

`one canonical semantic meaning → many domain projections → many SWIRM implementations → contextual TEAM compositions`

No provider, application, model, queue, database, payment rail, hosting system or protocol becomes constitutional merely because the ecosystem uses it.
